# Quality And Validation

## Purpose

This document defines the current verification baseline and the manual checks expected for each change category. It describes existing capabilities separately from future automation.

## Current Baseline

| Capability              | Current state                           |
| ----------------------- | --------------------------------------- |
| Production build        | `pnpm build`                            |
| Automated tests         | `pnpm test` with Node's built-in runner |
| Linting                 | `pnpm lint` (ESLint)                    |
| Formatting              | `pnpm format:check` (Prettier)          |
| Static type checking    | Not configured                          |
| Continuous integration  | GitHub Actions: lint, format, test, build on every push and pull request |
| Visual regression tests | Not configured                          |
| Performance benchmark   | `pnpm bench` (deterministic headless Chrome) and runtime telemetry (`getRenderStats()`) |

A successful Vite build proves that modules and assets can be bundled. It does not prove that WebGL shaders compile, the scene is nonblank, assets load in the browser, or controls work.

## Required Checks By Change

| Change area                    | Minimum checks                                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Documentation only             | Resolve Markdown links, run `git diff --check`, and inspect the rendered structure where practical.                                 |
| JavaScript or configuration    | Run `pnpm lint`, `pnpm format:check`, `pnpm test`, and `pnpm build`; load the app; check console and failed network requests.        |
| Terrain or chunk streaming     | Run tests and build; traverse multiple chunks and LODs; inspect bounded stats, seams, stalls, and lifecycle on desktop and mobile.  |
| GLSL, materials, or Three.js   | Build; inspect browser shader errors; visually check every affected material near and far from the plane.                           |
| UI, controls, camera, or audio | Build; complete the manual experience smoke test below with mouse and narrow/touch emulation as applicable.                         |
| Assets                         | Run `pnpm assets:encode` after changing a master; build; reload without cache; verify progress completion, network requests (KTX2 files and one transcoder `.wasm`, no JPEG), transforms, materials, and attribution files; compare close-ups with the previous build. |
| Dependencies                   | Update `package.json` and `pnpm-lock.yaml` together; build; run affected browser checks; review migration notes for major versions. |

Run narrower checks first when a task introduces them, but do not skip the production build for source, shader, dependency, or configuration changes.

`pnpm test` runs every `test/*.test.js` file in Node; `test/support/` registers a hook that resolves extensionless imports, `?url` imports (to their path), and `.glsl` imports (with their file includes), so tests import the same modules Vite bundles. The suites:

Browser lifecycle checks can read `window.__INFINITE_WORLD__.getChunkStats()`, which also reports `headingSector`, `sceneryChunks`, and `sceneryInstances`. For streaming changes, also hold a turn: `headingSector` should step through all eight sectors, and the queue should drain after each step with `stale` staying low. Climb to the maximum altitude and check that no LOD seam is visible ahead. After the queue drains, `live` must equal `desired`, `pending`, `queued`, `inFlight`, and `ready` must return to zero, `created - disposed` must equal `live`, `generated` must be at least `created`, and `failed` must remain zero. `lastCommit.bytes` stays within `CHUNK_STREAMING.commitBytes` except when a single result is larger. Desktop reports half its logical cores as workers (one to four); mobile reports one. Generated terrain must look identical to the previous build at the same seed: the grid, heights, and normals are bit-identical by design. The rocky coast relief is the exception: setting **Terrain > Coast > Relief height** to `0` restores the previous heights exactly.

Flight checks can read `window.__INFINITE_WORLD__.getFlightStats()`. Use `pointerYRatio`, `verticalInput`, position Y, speed, manual/visual speed effects, camera FOV/Z, corridor limits, minimum-altitude jump, terrain-brake impulse/effect, and target/effective terrain slowdown to distinguish actual flight changes from camera motion.

## Manual Experience Smoke Test

Use a fresh page load and check:

1. The loader appears, progresses, and disappears. With the airplane GLB blocked (DevTools request blocking), the loader gives way to "The airplane could not be loaded." and a focused **Retry** button that reloads the page; nothing else starts and no exception is thrown. With the wood texture blocked, the experience still starts, with plain vertex colors on scenery and clouds.
2. The canvas renders nonblank terrain with no console errors or failed requests (the page declares an empty favicon, so there is no `favicon.ico` 404). The network panel shows the airplane GLB and its `-shadow.glb` caster once each, with no "preloaded but not used" warning; with `?plane=toy` only `plane-toy.glb` and `plane-toy-shadow.glb` load. Without `?gui=1` and `?debug=1`, no `debugGui` or `flightPauseDebug` chunk is requested.
3. The play action starts movement and soundtrack playback. With `?debug=1` or `?gui=1`, before Play `getFlightStats().speed` is `0`, the position stays put, and moving the pointer or the wheel neither turns, climbs, nor boosts the airplane; **Start experience** accelerates it from `0` and gives the controls back. Without either flag the airplane cruises before Play. The loader does not wait for the soundtrack; with the network throttled, Play still appears once the airplane and wood texture have loaded.
4. Pointer movement turns and rolls the airplane; above `45%` it climbs, from `45%` through `65%` it settles at the reached altitude, and below `65%` it descends. Repeat with touch in a mobile viewport.
5. At cruise, a light edge blur and chromatic aberration are visible (`getPostProcessingStats().speedEffectIntensity` about `0.259`) while the FOV stays at its base value. Scrolling down produces acceleration that reaches its full strength in about `0.3` s and holds while scrolling continues, with camera movement, FOV expansion, wider trails, and a stronger edge blur with chromatic aberration that leaves the center sharp; after the last wheel event it decays smoothly back to the cruise minimum over a few seconds. At cruise speed, make a moderate turn and confirm no trail appears, then turn sharply in both directions and confirm both trails follow the wing tips, the outer wing's trail is wider, and turn-only width remains below the full-boost width. At maximum boost the trails should reach full width. The flown path should remain without visible stepping for about `60` world units. Each stripe should grow from zero thickness, reach its maximum near the middle, then narrow to zero at the tail; both edges should be visibly irregular near the middle but gradually smoother toward both ends, with a thin dark outline. The thinnest projected sections should become slightly translucent without an abrupt cutoff or obvious flicker. Scrolling up produces gentler braking and the opposite camera/FOV response without a new acceleration trail or post-processing effect. Once the boost fades, `getPostProcessingStats().active` returns to `false`. The film grain stays visible and does not move or flicker in either state. With `?gui=1`, **Film grain > Intensity** changes it live, and `0` removes it. Cycle every **Tone mapping > Mode** and change **Day exposure** (by day) and **Night exposure** (at night): the scene and sky change together without console errors, and holding **Speed effect > preview** above `0` keeps the same brightness and contrast (no pop between the idle and active paths). `getPostProcessingStats().frameBufferType` is `1016` (half float) with a tone-mapped mode, including the default ACES Filmic, and `1009` (8-bit) with None.
6. With `?gui=1`, change all **Trails** sliders while a trail is visible. Ribbon width must move both stripes, line and border width must change their respective thicknesses, and each edge's frequency and amplitude must change that edge independently. **Oscillation** frequency and amplitude must move the stripe centerlines in slightly different patterns without moving their attachment points at the wings or changing edge noise. On a straight boosted run with level wings, the trail should not oscillate; bank the airplane progressively and confirm the newly emitted sections oscillate more, with maximum motion at maximum bank and no shader error.
7. The sound control mutes and restores volume.
   Debug pause: without `?debug=1`, **P** does nothing and `getDebugStats()` is `null`. With `?debug=1`, **P** during the play intro is ignored. After the intro, **P** stops the airplane, water and `uTime` animation keep moving, and the orbit camera rotates, pans, and zooms. Panning moves across the ground like a map: dragging vertically moves forward and back, not up and down, and the camera height stays the same. The wheel must not change `getFlightStats().speedEffect`. Pressing **P** again returns the camera to its exact follow position without a jump. With `?debug=1&gui=1`, typing `p` into a GUI text field must not toggle the pause. On touch, orbiting while paused must not make the airplane turn after resume. Switching to another tab mid-flight and back resumes the flight without a jump, and the airplane stays visible. Clouds keep their place while flying, with no pop at the field edge. Boats appear with the scenery of new chunks and keep their place.

## Terrain And Rendering Observations

For performance-sensitive work, record conditions rather than reporting a subjective improvement:

- Browser and device.
- Viewport and device pixel ratio.
- Desktop or mobile code path.
- Chunk radius and relevant terrain parameters.
- Approximate frame time before and after the change.
- Whether the test crossed chunk boundaries and exercised multiple LODs.

Do not increase chunk radius, geometry density, cloud density or field radius, or shader cost based only on a high-end desktop result.

### Frame Telemetry

`window.__INFINITE_WORLD__.getRenderStats()` (see [Architecture](ARCHITECTURE.md#stats-api)) reports frame intervals, main-thread time per frame-loop stage, whole-frame draw calls and triangles, and GPU time where `EXT_disjoint_timer_query_webgl2` exists. Call it once to start GPU timing, fly for at least ten seconds (the window holds `600` frames), and read it again.

- The `render` stage includes waiting for the GPU when the driver applies back-pressure, so on a GPU-bound frame it approaches the frame interval. Compare `cpu` with `frame` to tell CPU-bound from GPU-bound frames.
- On ANGLE Metal (Chrome on macOS) the timer query spans queued work too and reads about twice the frame interval. Compare GPU times only between builds in the same browser, never as absolute costs.

### Comparing Builds

GPU changes on a fast desktop GPU only show when the frame is GPU-bound. `pnpm bench` ([`scripts/bench.mjs`](../scripts/bench.mjs), Node 22+ and Chrome) automates the method used for the Phase 3 measurements in the [project review](reviews/2026-10-02-project-review.md):

- It builds the working tree, and with `--compare <git-ref>` that ref in a temporary git worktree (removed afterwards; it reuses the repository's `node_modules`), and serves each build with `vite preview`.
- Headless Chrome runs with `--disable-gpu-vsync --disable-frame-rate-limit` in a single tab (other tabs, including another Chrome on the same machine, share the GPU and inflate the times), by default a `1920 × 1080` viewport at device pixel ratio `2` (a `3840 × 2160` canvas) and `?seed=s762&time=0.35&dpr=2`, so the adaptive resolution stays off.
- A deterministic flight: an injected script advances the page's `requestAnimationFrame` timestamps and `Date.now` (gsap) by exactly `1/60` s per frame, clicks Play on the first frame it is visible after `init()`, and measures the real time of frames `300` to `900` after the click. Builds alternate for `--rounds` rounds. Every build renders the same frames, and the mean frame time is the comparison metric. The first few hundred frames after load are not GPU-throttled while the canvas fades in, and Chrome's compositor sometimes delivers two frames together (a `~40` ms interval followed by a `~0` ms one), which moves the p95 more than the mean.
- `--shots <dir>` stops advancing time `400` frames after Play, waits for chunk streaming to converge, reads the canvas with `toDataURL()` inside the frame callback (a CDP screenshot can show a stale frame), and prints the PSNR between the builds. Since the loop clock starts on its first frame, two runs of one build give bit-identical captures; a ref from before that change differs by its start time of day. `--rounds 0` only captures. Each capture also prints the held frame's draw calls and triangles, which compare builds exactly; two builds can still differ by one far-cascade render (about `12` draw calls), since that cascade renders every other frame and the capture frame's parity is not fixed.
- Console errors of each run are printed; `--verbose` adds warnings and `getRenderStats()`.
